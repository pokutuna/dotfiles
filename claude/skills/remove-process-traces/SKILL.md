# Remove Process Traces

対話しながら作ったドキュメントやコードコメントには、それを生んだ会話が染み出す。会話を知らない人が読んでも、自然で独立した成果物として立つように書き直す。

## 観点 1: 現在のセッションのユーザではなく、将来の読者に向けて書く

指示を出したセッションのユーザは依頼者であって、読者そのものではない。成果物の中の「あなた」は将来の読者を指す。

- 依頼者への応答が紛れ込んでいないか: 「ご指摘のとおり修正しました」「ご要望に沿って〜」
- 会話でしか通じない文脈に依存していないか: 会話中の略称・コードネーム、「例の件」、「今回はやらないことにした」
- 指示や制約が disclaimer として露出していないか。制約は設計に溶かす:
  - Bad: 「このガイドでは Git や CLI ツールは使いません」
  - Better: 「プロジェクトフォルダは Google Drive で共有します」
  - 「初心者向けに」という指示は「本書は初心者向けです」と書くことではなく、ペース配分・用語定義・例の充実として現れる
- 依頼者が意図を伝えるために出した例をそのまま内容にしていないか。例は診断材料であって最終コンテンツではない

## 観点 2: 試行錯誤の過程をクリーンアップする

反復で作ったものには製作過程の地層が残る。最終形だけを残す。

- 放棄したアプローチの残骸: 使われていないコード・関数・設定、方針転換前の節、コメントアウトされた旧実装
- 経緯のナレーション: 「当初は〜を検討したが」「前の版と異なり」「〜に変更しました」。設計判断として読者に価値があるものだけ、Alternatives Considered 等の適切な置き場に読者向けの言葉で書き直す
- 継ぎ接ぎの不整合: 部分修正を重ねた結果の、節ごとのトーン・用語・詳細度のばらつき。全体を単一の声に揃える
- 作業の残り物: セッション用の TODO/FIXME、デバッグ出力、動作確認の仮データ、プレースホルダのままの箇所

逆に、文書の正規の置き場に読者向けの言葉で置かれた記述は痕跡ではない。Alternatives Considered 型の比較や「〜しない」ことの根拠、Open Issues 等のステータス節、スコープ宣言 (Non-Goals) は残す。反復で内容が拡張されて古い記述が現在の内容と矛盾している場合は、削るのではなく実態に合わせて整合させる。

## 判断基準

残すか消すか迷ったら「この一文は読者の役に立つ情報か、それとも成果物がなぜこうなったかの説明か」。後者は消すか、設計に溶かす。

## 出力

走査は依頼で指定された範囲 (差分・特定ファイル・文書単位) に限り、指定がなければ成果物全体を対象にする。説明するより書き直す。対象がファイルなら直接編集し、提案として求められた場合は修正箇所の before/after で示す。走査して直すべき箇所がなければ、変更をひねり出さずその旨と根拠を短く述べて終える。何を消したかの報告は求められない限りしない。成果物の目的・技術的な正しさ・読者に必要な要件は保持する。
