現在のセッションの引き継ぎドキュメントを作成し、現在の作業ディレクトリに保存せよ。

## ファイル名

```
HANDOVER-$(date +%y%m%dT%H%M).md
```

## 書き方の方針

これは経緯の要約ではなく、残りの作業のためのブリーフである。次のセッションで即座に作業を再開できるよう、簡潔かつ完全に書く — 重複作業や同じミスを防げる情報は積極的に含める。

- 残りの作業に関係する事実だけを選ぶ。会話で何度も出たことを、それだけで重要とみなさない
- 観測していないことを事実として書かない。推測や、自分で組み立てた次のコマンドは、そうと分かる形で書いてよい
- パス、シンボル、観測値、エラーは正確に書く
- ファイルや環境に残っているものは中身を写さず、パスやコマンドで指す。変更内容は要点だけ書き、詳細はファイルを見れば分かるようにする
- truncate された出力は、見えなかった部分を推測で埋めず、取り直す方法を書く

## ドキュメントの内容

### 1. Task Overview
- ユーザーの依頼: 最初の依頼と、その後に範囲や方針を変えた発言を原文で引用する。方針が変わった場合はどれが現行かを明記する
- 成功基準 (ユーザーが明言していなければ、依頼から導いたものだと分かるように書く)
- このタスクで指定された制約や clarification

### 2. Current State
- 完了済みの作業
- 作成・変更・分析したファイル(パス付き): ファイルごとに何を変えたかと、検証済みかどうか
- 実行した検証とその結果
- 生成した成果物

### 3. Important Discoveries
- 判明した技術的制約や要件
- 下した判断とその理由
- 発生したエラーと解決方法
- 試したが上手くいかなかったアプローチとその理由

### 4. Next Steps
- 残りのサブゴールを実行順に並べる
- すぐ次に実行するコマンドと、完了とみなす条件
- ブロッカーや未解決の疑問点

### 5. Context to Preserve
1〜4 に収まらず、次のセッションでも守るべきことだけを書く。1 に書いたことは繰り返さない。該当がなければ節ごと省いてよい。

- ユーザーの好みやスタイル要件 (コミットメッセージの言語など)
- ユーザーへの約束事 (制約とどちらか迷うものは 1 に書く)
- 自明でないドメイン固有の情報 (このタスクの技術的な事実は 3 に書く)
