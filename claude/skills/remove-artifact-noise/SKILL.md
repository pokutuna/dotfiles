# Remove Artifact Noise

対話しながら作った成果物には、依頼者への応答、途中で変更された方針、会話内だけで通じる表現が残りやすい。制作時の文脈を知らない人が読んでも、完成した成果物として自然に理解できるように書き直す。

## 将来の読者に向けて書く

成果物は、制作時の会話を知らない将来の読者にも理解できるように書く。依頼者との会話を前提にしない。

- 依頼者への返答を残さない。「ご指摘のとおり修正しました」「ご要望に沿って」などは削除し、修正後の内容だけを書く。
- 会話内の略称、コードネーム、「例の件」「今回はやらない」といった共有文脈に依存しない。
- 依頼者の指示を断り書きとして転記しない。指示に合わせて、構成、説明、手順を変える。
  - 修正前: 「このガイドでは Git や CLI ツールは使いません」
  - 修正後: 「プロジェクトフォルダは Google Drive で共有します」
- 初心者向けに書くよう指定された場合は、用語を定義し、手順を細かく分け、理解に必要な例を加える。「本書は初心者向けです」と書くだけで済ませない。
- 依頼者が挙げた例は、その意図を理解するために使う。例そのものが読者に必要でなければ、成果物には含めない。

## 制作過程ではなく最終状態を示す

修正を重ねた結果として残った古い記述を取り除く。文書全体を、最終的に採用した内容に合わせる。

- 文書やコメントに残った、放棄した方針や旧実装の説明を取り除く。
- 「当初は」「この文書の前版と異なり」「変更しました」など、成果物への修正を報告する記述を取り除く。
- 節ごとに文体、用語、説明の詳しさが異なる場合は、文書全体で統一する。
- 制作中だけ必要だった `TODO` や `FIXME`、デバッグ出力、仮データ、未完のプレースホルダーを取り除く。

古い記述が現在の内容と矛盾する場合は、現在の仕様や実装を確認して書き直す。読者に必要な情報が含まれている場合は、その情報まで削除しない。

意図的に先送りした判断や作業は削除しない。読者に必要であれば、実施しない理由と、実施する時期や条件を、未決定事項や今後の作業として記述する。

## 対象の経緯は残す

取り除くのは成果物を作った経緯であり、成果物が扱う対象の経緯ではない。対象が現在の状態になった理由を読者が理解できるように、以前の状態や変更理由を残す。設計判断の理由も残す。

例えば、次の情報は対象の経緯として残す。

- Design Doc では、採用した設計だけでなく、その判断を支える代替案、制約、トレードオフを記述する。
- 後方互換性を維持するために、アプリケーション内部の処理から参照されなくなったモデルのフィールドを残す場合がある。その場合は、コードコメントや技術文書に、フィールドが残っている理由を記述する。

制作時のやり取りそのものは残さない。例えば、「対話の途中で方法 A を検討し、問題が見つかったため方法 B に変えた」のように、検討の順序を説明しない。方法 A を採用しない理由が読者にも必要なら、対象の制約や設計判断として書き直す。

書き直した後も、成果物が目的と要件を満たし、技術的に正しいことを確認する。

## 読者が意味を推測しなくてよいように書く

書き手と依頼者にしか通じない表現を使わない。誰が何をし、なぜその結果になるのかが分かるように書き直す。

- 比喩が技術的な意味を隠していないか確認する。
  - 修正前: 「責務の境界が溶ける」
  - 修正後: 「複数のコンポーネントが同じ責務を持ち、変更箇所を特定できなくなる」
- 主語、目的語、判断の時点を省いた圧縮表現を具体化する。
  - 修正前: 「この判断を上流で回収する」
  - 修正後: 「この判断は、実装時ではなく設計時に行う」
- 条件、動作、理由、結果を一文や名詞の列挙に詰め込まない。読者が関係を追えるように文を分ける。
  - 修正前: 「認証方式の変更による旧クライアントへの影響を考慮する」
  - 修正後: 「認証方式を変更すると、旧クライアントはログインできなくなる。このため、移行期間中は以前の認証方式も受け付ける」
- 会話内で定義された語は、成果物内でも定義するか一般的な表現へ置き換える。

短くすること自体を目標にしない。読者が会話の文脈を推測したり、曖昧な表現の意味を補ったりせずに読めるようにする。説明を加えた結果として文章が長くなってもよい。意味を正確に伝える比喩や、意味が明確な短い表現は残す。

## 判断基準

対象の経緯は残し、成果物を作る過程で生じたやり取りは残さない。制作中に得た知見が読者にも必要なら、対象にどの制約があり、なぜその判断をしたのかを書く。どの記述も、制作時の文脈なしで理解できるようにする。

## 出力

- 依頼で指定された範囲だけを確認する。指定がなければ成果物全体を対象にする。
- 問題点を説明するだけで終わらず、対象の文章を書き直す。対象がファイルなら直接編集する。
- 提案として求められた場合は、修正箇所を修正前と修正後に分けて示す。
- 直すべき箇所がなければ無理に変更せず、理由を短く述べる。
- 削除内容は、求められない限り報告しない。
