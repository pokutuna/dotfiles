# 記述例 ── 注文を確定する

説明しやすい題材を使った記法のサンプル。注文処理の構造や項目をそのまま別ドメインの標準として採用するものではない。

```text
ユースケース名：注文を確定する
使用時の状況：購入者がカート内の商品と配送先を確認し、注文を確定しようとしている。
スコープ：通販サイト（注文システム）
レベル：ユーザー目的レベル
主アクター：購入者
支援アクター：決済代行サービス

利害関係者と利益：
  購入者 ── 選んだ商品を確実に注文し、二重に請求されない。
  当社 ── 在庫を伴わない注文を受けず、売上を回収する。
  倉庫 ── 出荷可能な確定注文だけを受け取る。

事前条件：購入者は認証済みで、カートに1点以上の商品が入っている。
最低保証：与信の要求と結果が記録され、課金と注文の状態が食い違ったまま放置されない。
成功時保証：注文が確定し、在庫が引き当てられ、与信が成立し、購入者と倉庫に通知される。
トリガー：購入者が注文の確定を指示する。

主成功シナリオ：
  1. 購入者は配送先と支払い方法を指定して、注文の確定を指示する。
  2. システムは、全商品に引き当て可能な在庫があることを確認する。
  3. システムは在庫を引き当て、注文を仮確定として記録する。
  4. システムは決済代行に与信を要求する。
  5. 決済代行は与信の成立を回答する。
  6. システムは注文を確定し、購入者と倉庫に注文内容を通知する。

拡張：
  2a. 一部の商品の在庫が不足している：
      2a1. システムは不足分を購入者に提示し、数量の変更または削除を求める。
      2a2. 購入者は注文内容を変更する。ステップ2に戻る。
      2a3. 購入者は注文を取りやめる。システムは処理を終了する。
  2-5a. 在庫、注文、決済の外部サービスへの要求または応答が規定時間内に完了しない：
        2-5a1. システムは要求と現在の処理状態を記録する。
        2-5a2. システムは購入者に処理が保留されたことを通知し、ユースケースを終了する。
  5a. 決済代行が与信の不成立を回答する：
      5a1. システムは引き当てた在庫を解放し、理由を購入者に提示する。
      5a2. 購入者は支払い方法を変更する。システムは注文内容を再確認し、ステップ2に戻る。
      5a3. 購入者は注文を取りやめる。システムは処理を終了する。
  *a. どこかの時点でシステムが利用不能になる：
      *a1. システムは処理途中の状態を保存できる場合に保存し、再開に必要な情報を記録する。
      *a2. システムは購入者に処理が保留されたことを通知する。

技術およびデータのバリエーション：
  決済代行との接続方式や要求データ形式が異なっても、与信結果と注文状態の扱いは同じとする。
```

## この例で示している判断

- 主成功シナリオを成功時保証までの一本道にしている。
- 在庫不足は `2a`: ステップ2固有の条件。
- 複数ステップに共通する外部サービスのタイムアウトは `2-5a`: 検出方法と最終的な扱いが同じ。
- どの時点でも起きるシステム障害は `*a`。
- 与信否決 (`5a`) は結果が異なるため、共通障害へ集約していない。

## 入れ子の例

拡張の処理自体に失敗がある場合:

```text
5a. 決済代行から応答が返らない：
    5a1. システムは要求と注文状態を記録する。
         5a1a. ログの保存に失敗する：
               システムは別の監査経路に障害を記録し、処理を保留する。
    5a2. システムは購入者に確認中であることを通知する。
```
