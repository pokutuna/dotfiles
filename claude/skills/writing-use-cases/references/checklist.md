# レビューチェックリスト

## 個別ユースケース

- [ ] 名前が能動的な目的を表している。
- [ ] スコープとレベルが明示され、本文と一致している。
- [ ] 主アクターが1つのロールになっている。
- [ ] 支援アクター、舞台裏の利害関係者、内部アクターを区別している。
- [ ] 使用時の状況が背景を示し、UI や内部設計になっていない。
- [ ] 事前条件はシステムが保証でき、本文で再確認していない。
- [ ] 最低保証と成功時保証が、利害関係者の利益を反映している。
- [ ] 主成功シナリオは3〜9ステップ程度で、トリガーから保証まで到達する。
- [ ] 各ステップの主語、意図、情報の受け渡しが明確である。
- [ ] 主成功シナリオに `if`、失敗、タイムアウトが混ざっていない。
- [ ] 拡張条件がシステムから検出可能である。
- [ ] `*a`、範囲指定、集約を、同じ処理になる場合だけ使っている。
- [ ] 拡張の合流先または終了状態が明確である。
- [ ] 技術・データのバリエーションと拡張を混同していない。
- [ ] 画面、API、データ、ルール、非機能要求へのリンクがある (該当する場合)。

## 複数のユースケースを扱う場合の全体確認

対象や目的に関係する項目だけ選んで使う。

- [ ] In/Out と対象システムの境界が合意されている。
- [ ] すべての利用者、運用者、外部システム、装置をアクター候補として確認した。
- [ ] 各主アクターの主要な目的を列挙した。
- [ ] 要約、ユーザー目的、サブ機能のレベルを整理した。
- [ ] 正常系だけでなく、失敗、取消、再試行、タイムアウト、期限切れを確認した。
- [ ] 権限不足、手動での代替、障害復旧、監査、通知を確認した。
- [ ] 同じ目的の重複、目的のない機能、ユースケースから参照されない機能を確認した。
- [ ] 画面、外部インターフェイス、バッチ、イベント、データ、ビジネスルール、非機能要求に未対応の項目がない。
- [ ] 未決定事項に、決定者と確認期限がある。

## 完了判定

次の2者が確認して初めて完了とする。

- 利用側・スポンサー: 望んでいる振る舞いと利益が漏れていない。
- 開発・テスト側: 記述された振る舞いを実装し、テストできる。

文章の表現を整えることより、未決定のルール、外部連携、失敗時の約束、全体の抜けを残さないことを優先する。
