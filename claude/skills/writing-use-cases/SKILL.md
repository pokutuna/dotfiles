# ユースケース記述

1本のユースケースを、読み手が理解でき、利害関係者が確認でき、開発者が実装できる形に記述するための skill。

Alistair Cockburn『Writing Effective Use Cases』(邦訳『ユースケース実践ガイド』) を参考書籍とし、その考え方に基づく。同書は唯一の必須テンプレートや一律の厳密さを定めていない。ここのテンプレートや項目は土台であり、目的とリスクに応じて増減してよい。

## 前提となる概念 (最小限)

記述に入る前に、次の3点が決まっているか確認する。決まっていなければユーザーに確認するか、対象の資料から読み取って明示する。

- **スコープ**: どの境界をブラックボックスとして扱うか (企業・組織 / システム群 / アプリケーション / サブシステム)。内部構造を推測して書かない。
- **レベル**: 目的の高さ。
  - 要約: 数時間〜数か月の成果。複数の目的を束ねる (例: 商品を購入する)
  - ユーザー目的: 1人が1か所で中断なく達成できる数分程度の目的 (例: 注文を確定する)。**記述の基本はこのレベル**
  - サブ機能: 単独では利用者が満足しない数秒程度の処理 (例: 顧客を検索する)
- **アクター**:
  - 主アクター: 目的を持ち対話を開始するロール (人に限らず組織・システムも)
  - 支援アクター: 対象システムにサービスを提供する外部の人・組織・システム
  - 舞台裏の利害関係者: 直接対話しないが結果に利益を持つ者 (法令、会計、監査など)

複数のユースケースを洗い出す段階なら、本文を書く前にアクター-目的リストを先に作り、全体の抜け・重複・レベル混在を確認してから詳細化する対象を選ぶ。段階的な手順は [references/discovery.md](references/discovery.md) を参照。

## 1. 記述の原則

> ユースケースとは、システムの振る舞いについての利害関係者間の約束である。

- 主アクターの目的から始める。
- 対象システムはブラックボックスとして扱う。
- 主成功シナリオは一本道にする。分岐、失敗、代替、取り消し、タイムアウトは拡張に分ける。
- UI 操作ではなく、アクターの意図とシステムの応答を書く。
- 成功だけでなく、どんな終わり方でも守る最低保証を書く。
- テキストが本体であり、ユースケース図は目次や関係の補助である。

## 2. テンプレート

### 完全形式

```text
ユースケース名：<能動態の動詞句で、達成したい目的を表す>
使用時の状況：<誰が、どのような状況で目的を達成しようとしているか>
スコープ：<ブラックボックスとして扱う対象システム>
レベル：<要約 / ユーザー目的 / サブ機能>
主アクター：<目的を持って対話を開始する1つのロール>
支援アクター：<対象システムにサービスを提供する外部アクター>
利害関係者と利益：
  <関係者> ── <守られるべき利益>
事前条件：<開始前にシステムが真だと保証する状態>
最低保証：<どんな終わり方をしても守る状態>
成功時保証：<目的が達成されたときの状態>
トリガー：<開始させるイベント。時間イベントも可>
主成功シナリオ：
  1. <アクター> は <意図> する。
  2. <システム> は <観測できる結果> する。
拡張：
  2a. <検出可能な条件>：
      2a1. <対処>
技術およびデータのバリエーション：
  <振る舞いは同じで、実現方法だけが異なる点>
関連情報：<優先度、頻度、性能、ビジネスルール、リンク、未決定事項>
```

### 略式

会話が密なチーム、要求の発掘、規模の見積もりでは短く書く。略式でも目的と対象が分かる情報を残す。

```text
ユースケース名：<目的>
スコープ：<対象>
レベル：<要約 / ユーザー目的 / サブ機能>
主アクター：<ロール>
概要：<目的と主な振る舞いを2〜6文>
重要な拡張：<失敗・代替・取り消しなど>
未決定事項：<確認が必要なこと>
```

### 各欄の判定

| 欄 | 書くこと | 避けること |
|---|---|---|
| ユースケース名 | 主アクターの目的。能動的な動詞句 | 「注文管理機能」のような機能名 |
| 使用時の状況 | 目的が生じる背景 | 画面構成や内部処理 |
| スコープ | 対象の境界 | 内部コンポーネントの推測 |
| レベル | 要約・ユーザー目的・サブ機能 | レベルの違う処理の混在 |
| 主アクター | 目的を持つ1つのロール | 複数の人を並べること |
| 支援アクター | サービスを提供する外部の人・装置・システム | 対象システムの内部部品 |
| 利害関係者と利益 | 振る舞いの結果として守る利益 | 「検索機能がある」のような解決策 |
| 事前条件 | システムが開始前に保証する状態 | 本文で再確認する条件 |
| 最低保証 | 失敗しても守る状態 | 「何も起きない」のような空の約束 |
| 成功時保証 | 目的達成後の状態 | 完了画面の表示だけ |
| トリガー | 開始イベント | 開始後の詳細手順 |
| 主成功シナリオ | 成功までの一本道 | `if` や失敗処理 |
| 拡張 | 検出可能な条件と処理 | 実装不能な原因の断定 |
| 技術・データのバリエーション | 振る舞いを変えない実現方法の差 | 成功・失敗の分岐 |

## 3. レベルと粒度

ユーザー目的レベルの目安:

- 1人が1か所で、中断なく達成できる。
- 数分程度で終わる。終了時に利用者が目的を達成したと判断できる。
- 主成功シナリオは3〜9ステップ程度に収まる。

「ログインする」「在庫を確認する」はサブ機能になりやすい。「通販サイトを利用する」は大きすぎる要約になりやすい。ステップが長くなったら、まず「なぜこれをしているのか」と問い、サブ機能をユーザー目的に統合できないか検討する。別ユースケースへの切り出しは、複数箇所から再利用する場合か、記述が読みにくくなる場合に限る。

## 4. シナリオの書き方

各ステップをアクターまたはシステムから始め、主語を明示する。外部システムとの往復は、誰が要求し、誰が応答したかが分かるようにステップを分ける。

```text
1. 購入者は配送先と支払い方法を指定して、注文の確定を指示する。
2. システムは、全商品に引き当て可能な在庫があることを確認する。
3. システムは在庫を引き当て、注文を仮確定として記録する。
4. システムは決済代行に与信を要求する。
5. 決済代行は与信の成立を回答する。
6. システムは注文を確定し、購入者と倉庫に注文内容を通知する。
```

書き換え規則:

- 「住所が入力される」のような受動態 → 主語のあるステップに
- 「取得ボタンを押す」のような UI 操作 → アクターの意図に
- 「システムは内部テーブルを更新する」のような内部設計 → 外から観測できる結果に

完全形式へ詳細化する順番の一例: 名前・スコープ・レベル・主アクター → 利害関係者と利益・事前条件・保証 → トリガーと主成功シナリオ → 失敗条件と代替成功条件の列挙 → 拡張の処理・合流先・終了状態 → バリエーションと関連情報。

## 5. 拡張の書き方

拡張は「検出可能な条件」「処理」「合流または終了」を持つ。`2a` はステップ2で発生する拡張、`2a1` はその処理の1ステップ。`2a` と `2b` の文字順に優先度や発生順序の意味はない。

### 記法の使い分け

| 記法 | 使う場面 |
|---|---|
| `2a.` | ステップ2で発生する条件 |
| `2-5a.` | ステップ2〜5のどこで発生しても、検出方法と最終的な扱いが同じ条件 |
| `*a.` | どの時点でも起こりうる障害。どの時点でも同じ処理になる場合だけ使う |

ステップごとに保証や回復方法が異なる場合は、範囲指定や `*a` にまとめず `2a`、`3a` と分ける。

### 失敗の集約条件

複数のステップで起きる失敗を1つの拡張へ集約できるのは、次を全て満たす場合だけ。

- システムが同じ種類の事象として検出する。
- 処理、通知、ログ、終了状態が同じである。
- 利害関係者の利益や最低保証が変わらない。

集約の目的は文章を短くすることではなく、同じ要求を重複して保守しないこと。

### 入れ子

拡張の処理自体の失敗は入れ子にする (`2a1a.`)。入れ子が深くなりすぎたり複数箇所から同じ処理を使う場合は、別ユースケースへの切り出しを検討する。切り出しても、呼び出し側には失敗時の扱いを残す。

### 拡張とバリエーションの区別

| 内容 | 置き場所 |
|---|---|
| 在庫不足、与信否決、取り消し、タイムアウト (結果や振る舞いが変わる) | 拡張 |
| 同じ結果を別の通信方式・データ形式で受け取る (振る舞いは同じ) | 技術・データのバリエーション |
| 複数箇所から共通利用し、単独の目的として扱える処理 | 別ユースケース |

### ユースケース間の関係

必要になったときだけ使う。迷ったら、まず通常のステップや拡張として書けないか確認する。`include` は基底側が呼び出しタイミングを知っている場合、`extend` は拡張側が割り込みタイミングを知っている場合。混在は混乱のもとなので、関係を使う場合は採用理由とトリガーを記述する。

## 6. 作業の進め方

1. スコープ・レベル・主アクターを確認する (不明ならユーザーに確認)。複数のユースケースをゼロから洗い出す場合は、先に [references/discovery.md](references/discovery.md) の手順で全体を整理し、詳細化する対象を選ぶ。
2. 採用する形式 (完全形式 / 略式) を目的に合わせて選ぶ。合意・実装・テストにつなぐなら完全形式、要求の発掘や見積もりなら略式。
3. テンプレートに沿って記述する。記述例は [references/example.md](references/example.md) を参照。
4. セルフレビューとしてチェックリスト ([references/checklist.md](references/checklist.md)) を適用し、満たさない項目を修正する。
5. 未決定事項 (業務ルールの具体的な数値、外部連携の仕様など、記述者が決められないこと) は推測で埋めず、関連情報欄に決定者とともに明記する。

完了の判断は文章を磨き切ることではない。未決定のルール、外部連携、失敗時の約束、全体の抜けを残さないことを優先し、最終的には利用側 (振る舞いと利益に漏れがない) と開発・テスト側 (実装・検証できる) の両者の確認をもって完了とする。
