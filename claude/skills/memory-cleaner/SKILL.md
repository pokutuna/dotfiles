# Memory Cleaner

プロジェクトの永続メモリを **棚卸し → トリアージ → ユーザ確認 (1回) → バックアップ → 適用 → 報告** の順で掃除する。

## 対象の特定

対象は**現在のセッションのメモリディレクトリ**。システムプロンプトの `# Memory` 節に記載されているパス (`~/.claude/projects/<slug>/memory/`) をそのまま使う。cwd からパスを推測・導出しない。別プロジェクトのメモリは対象にしない。

ディレクトリが空、またはメモリが 2〜3 件しかない場合は掃除の必要がない旨を報告して終わる。

## 大原則

- **スコープは memory の操作。** リポジトリや CLAUDE.md への書き込みは、承認された relocate 提案 (手順 3) に限る。
- **判断と適用を分ける。** 全件を読んで台帳を作ってから処遇を決める。読みながらその場で消さない。個別には些細に見えるメモリが、複数のメモリに共通する上位原則の一例であることがあり、keep / delete / merge は全体を見ないと決められない。
- **鮮度は「現実との照合」で判定する。** 作成日や内容の印象ではなく、メモリが言及するパス・コマンド・値・事実が今も成り立つかをリポジトリや `~/.claude` で実際に確認する。腐敗の大半はこれで機械的に検出できる。
- **削除候補は 2 種類を区別する。** 検証ベース (参照先の消滅、事実の矛盾、反映済み) は根拠つきで自信を持って提案する。価値判断ベース (些細すぎる、もう使わない) は判断をユーザに委ねる。
- **削除・書き換えは必ずユーザの承認後。** 確認は 1 回にまとめる。
- **平易化で事実を落とさない。** 変えるのは表現だけ。パス・コマンド・値・日付は一字も落とさない。
- **重い作業はサブエージェントにオフロードする。** 棚卸し・検証と機械的な書き換えは `Agent` (model: sonnet) に出し、メインセッションはトリアージ・ユーザ確認・成果物レビューに専念する。サブエージェントはユーザに質問できないので、確認ステップは必ずメインセッションで行う。

## 手順

### 1. 現状を測る

```sh
MEMDIR=<システムプロンプト記載のメモリディレクトリ>
ls -la "$MEMDIR"; wc -c "$MEMDIR"/*.md
```

ファイル数・合計バイト数・MEMORY.md 単体のバイト数を before として記録する。MEMORY.md は毎セッション context に読み込まれるので、そのサイズが応答劣化への寄与が最も直接的な数字になる。

### 2. 棚卸し — 台帳を作る (read-only)

サブエージェント (model: sonnet) にオフロードする。件数が多い (目安 15 件超) 場合はファイルを分割して並列に出す。各メモリについて以下を調べさせ、台帳として受け取る:

- frontmatter (`name` / `description` / `metadata.type`) と本文の要点
- 経過日数 (Read 時に付くリマインダー、または `mdls -name kMDItemFSCreationDate`。sandbox では `stat -f '%SB'` が失敗することがある)
- **鮮度検証**: 言及するファイルパス・コマンド・フラグ・バージョン・事実関係が、対応リポジトリや `~/.claude`、実環境で今も成り立つか。`rg` / `fd` / 実ファイルの Read で確認した結果を根拠つきで
- **反映済みか**: 内容がリポジトリの docs / CLAUDE.md / skill に既に書かれていないか (「〜に反映済み」と自記しているものは典型)
- 内容が重なる・同じ上位原則から派生しているメモリの組
- スタイル問題: 圧縮表記 (記号羅列・矢印チェーン・1 文への詰め込み)、独自の比喩・レトリック・擬人化、本題から逸れた追記、初見で意味が取れない略語
- index との整合: MEMORY.md からのリンク漏れ、実体のないリンク、`[[link]]` の表記ゆれや未解決参照
- frontmatter の世代差: `name` とファイル名の不一致、現行仕様 (type は user / feedback / project / reference) から外れたもの

サブエージェントには対応リポジトリのパスを伝え、リポジトリは読み取り専用で扱わせる。

### 3. トリアージ

台帳を見て、メインセッションで各メモリを分類する:

| 処遇 | 判断基準 |
|---|---|
| **delete (検証ベース)** | 参照先が消えた / 記載事実が現実と矛盾 / repo・docs・skill に反映済み / 完了したタスクの記録 |
| **delete (価値判断)** | 些細すぎる、状況が変わってもう使わない — ユーザに聞く |
| **merge** | 同じ上位原則の具体例が複数ある → 統合後の文面案を作る |
| **rewrite** | 内容は有効だが表現に問題がある |
| **keep** | そのまま残す |

事実が現実と食い違うが知見自体は有効なもの (例: バージョン番号だけ古い) は delete ではなく rewrite (事実の更新) にする。

このスキルのスコープは memory の操作であり、リポジトリ側のファイルは変更しない。ただし、メモリよりふさわしい置き場が明らかにあるもの (チーム全員に効くべき制約 → プロジェクトの CLAUDE.md や docs、プロジェクトに依らない知見 → global 側) は、**オプショナルな提案として** relocate (移管) を添えてよい。承認されたら移管してメモリを消す。いまいちそうなら memory のまま keep / rewrite で扱う (不要なら当然 delete)。

### 4. ユーザ確認 — 1 回にまとめる

全案を一覧で提示する: 各メモリの「名前 / 処遇案 / 根拠 (検証結果の引用)」。「消す」と「X に統合して残す」は同じメモリへの代替案なので、別々に聞かず並べて見せる。

件数が多い場合は 1 件ずつ聞かない。処遇グループ単位でまとめ、AskUserQuestion (multiSelect) で「このグループを承認 / 除外したい項目がある」の粒度で聞く。除外指定があった項目だけ個別に扱う。

relocate の提案は「移管先と追記内容」をここで見せて承認を取る。承認されなければ memory 内での処遇 (keep / rewrite / delete) に戻す。

### 5. バックアップ

適用前に必ず取る。メモリディレクトリは git 管理外で undo 手段がない。

```sh
cp -r "$MEMDIR" <scratchpad>/memory-backup-$(date +%Y%m%d-%H%M%S)
```

復元コマンドを報告に含める。

### 6. 適用 — 削除 → 統合・移管 → 平易化 → index 再生成

この順序を守る。消すものを書き直さない、統合で文面が変わるものを先に平易化しない。

1. **削除**: 承認されたものだけ `rm` する
2. **統合・移管**: merge は統合後ファイルを書き、元ファイルを消す。relocate は承認された場合のみ、移管先に書いてからメモリを消す
3. **平易化** (サブエージェントにオフロード可): 生き残った rewrite 対象を書き直す。ルール:
   - 検証可能な事実 (パス・コマンド・値・日付・エラーメッセージ) は一字も落とさない。変えるのは表現だけ
   - 圧縮表記・矢印チェーン・1 文への詰め込みをやめ、完結した文にする
   - 独自の比喩・レトリック・擬人化 (「犯人」「噛み合う」等) を、プロジェクトやリポジトリで使われている平易な語彙に置き換える
   - 相対日付は絶対日付にする
   - 本題から逸れた追記・別件の TODO は、価値があれば独立したメモリに分離し、なければ削る
   - frontmatter を現行仕様に正規化する: `name` = ファイル名 (拡張子なし)、`description` は 1 行、`metadata.type` は user / feedback / project / reference のいずれか。既存の他のキーは残す
   - feedback / project は本文に **Why:** と **How to apply:** を持たせる
4. **レビュー**: サブエージェントの書き換え結果は必ずメインセッションで Read し、事実の欠落・改変がないか元の文面と突き合わせる
5. **index 再生成**: MEMORY.md を作り直す。1 メモリ 1 行 (`- [タイトル](file.md) — 要点`)、index に本文を書き込まない (直書きされた知見はファイルに昇格するか統合済みのはず)。全ファイルが index に載っていること、リンク先が実在すること、本文中の `[[link]]` が残存メモリの `name` と一致することを確認する

### 7. 報告

- before / after: ファイル数・合計バイト数・MEMORY.md のバイト数
- 削除・統合・移管・書き換えの一覧 (それぞれ 1 行で)
- バックアップの場所と復元コマンド
- 次回の目安: MEMORY.md が 5KB またはメモリ 20 件を超えたら再実行を勧める
