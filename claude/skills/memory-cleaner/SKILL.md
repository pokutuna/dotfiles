# Memory Cleaner

プロジェクトの永続メモリを **棚卸し → トリアージ → ユーザ確認 (1回) → バックアップ → 適用 → 報告** の順で掃除する。

## 対象の特定

対象は**現在のセッションのメモリディレクトリ**。システムプロンプトの `# Memory` 節に記載されているパス (`~/.claude/projects/<slug>/memory/`) をそのまま使う。cwd からパスを推測しない。別プロジェクトのメモリは対象にしない。

ディレクトリが空、または個別メモリ (MEMORY.md を除く) が 3 件以下の場合は掃除の必要がない旨を報告して終わる。

## 大原則

- **スコープは memory の操作。** リポジトリや CLAUDE.md に書き込むのは、ユーザに承認された relocate (手順 3) だけ。
- **判断と適用を分ける。** 全件を読んで台帳を作ってから処遇を決める。読みながらその場で消さない。個別には些細に見えるメモリが複数のメモリに共通する上位原則の一例であることがあり、keep / delete / merge は全体を見ないと決められない。
- **鮮度は「現実との照合」で判定する。** 作成日や内容の印象ではなく、メモリが言及するパス・コマンド・値・事実が今も成り立つかをリポジトリや `~/.claude` で実際に確認する。
- **削除候補は 2 種類を区別する。** 検証ベース (参照先の消滅・事実の矛盾・反映済み) は根拠つきで提案する。価値判断ベース (些細すぎる・もう使わない) は判断をユーザに委ねる。
- **削除・書き換えは必ずユーザの承認後。** 確認は 1 回にまとめる。
- **平易化で事実を落とさない。** 変えるのは表現だけ。パス・コマンド・値・日付は一字も落とさない。
- **重い作業はサブエージェントにオフロードする。** 棚卸しと機械的な書き換えは `Agent` (model: sonnet) に出し、メインセッションはトリアージ・ユーザ確認・成果物レビューを行う。サブエージェントはユーザに質問できないので、確認は必ずメインセッションで行う。

## 手順

### 1. 現状を測る

```sh
MEMDIR=<システムプロンプト記載のメモリディレクトリ>
ls -la "$MEMDIR"; wc -c "$MEMDIR"/*.md
```

ファイル数・合計バイト数・MEMORY.md (index、以下同じ) 単体のバイト数を before として記録する。MEMORY.md は毎セッション context に読み込まれるため、そのサイズが最も重要な数字。

### 2. 棚卸し — 台帳を作る (read-only)

検証をサブエージェント (model: sonnet) にオフロードする。件数が少なければ本文はメインセッションで読み、現実との照合だけを出す分担でよい。15 件を超える場合はファイルを分割して並列に出す。読み取り範囲はメモリディレクトリ・対応リポジトリ・`~/.claude` の設定類に限る。対応リポジトリのパスは slug (元のプロジェクトパスの区切りを `-` に置換したもの) から復元して伝え、読み取り専用で扱わせる。検証で秘密の値 (キー・トークン) は読まない・出力しない。読まずに検証できない事実は捏造せず「検証不能」と台帳に記録する。

台帳には各メモリについて以下を記録させる:

- frontmatter (`name` / `description` / `metadata.type`) と本文の要点
- 経過日数 (Read 時に付くリマインダー、または `mdls -name kMDItemFSCreationDate`。取れなければ省略)
- **鮮度検証**: 言及するパス・コマンド・フラグ・バージョン・事実関係が今も成り立つか。`rg` / `fd` / 実ファイルの Read で確認した根拠つきで
- **反映済みか**: 内容がリポジトリの docs / CLAUDE.md / skill / 設定・実装そのものに既に反映されていないか
- 内容が重なる・同じ上位原則から派生しているメモリの組
- スタイル問題: 圧縮表記 (記号の羅列・矢印チェーン・1 文への詰め込み)、比喩・擬人化、本題から逸れた追記、初見で意味が取れない略語
- index との整合: リンク漏れ、実体のないリンク、`[[link]]` (本文中で他メモリの `name` を指すリンク記法) の未解決、index に本文として直書きされた知見
- frontmatter の世代差: `name` とファイル名の不一致、現行仕様 (type: user / feedback / project / reference) から外れたもの

### 3. トリアージ

台帳を見て、メインセッションで各メモリの処遇を決める:

| 処遇 | 判断基準 |
|---|---|
| **delete (検証ベース)** | 参照先が消えた / 記載事実が現実と矛盾 / repo・docs・skill に反映済み / 完了したタスクの記録 |
| **delete (価値判断)** | 些細すぎる、状況が変わってもう使わない — ユーザに聞く |
| **merge** | 同じ上位原則の具体例が複数ある → 統合後の文面案を作る |
| **promote** | index に直書きされた未反映の知見 → 意味のまとまりごとに個別ファイルへ昇格し、index は 1 行リンクにする。行単位で機械的に切らず、関連する断片は 1 ファイルに束ねる |
| **rewrite** | 内容は有効だが、事実の一部が古い、または表現に問題がある |
| **keep** | そのまま残す |

rewrite にするものは、本題から逸れた追記を独立したメモリに分離するか削るかもここで決めておく。「検証不能」は削除の根拠にならない。検証不能な知見を残すかどうかは価値判断としてユーザに委ねる。

メモリよりふさわしい置き場が明らかにあるもの (チーム全員に効くべき制約 → プロジェクトの CLAUDE.md や docs、プロジェクトに依らない知見 → global 側) には、オプションとして **relocate (移管)** 案を添える。承認されたら移管先に書いてからメモリを消し、承認されなければ memory 内の処遇 (keep / rewrite / delete) にする。

### 4. ユーザ確認 — 1 回にまとめる

全案を「名前 / 処遇案 / 根拠 (検証結果の引用)」の一覧で提示する。同じメモリへの代替案 (消す / 統合して残す) は別々に聞かず並べて見せる。relocate は移管先と追記内容もここで見せる。index の修復 (リンク漏れ・切れ・重複行) が必要な場合は、それも一覧の 1 項目として出す。

件数が多くても 1 件ずつ聞かない。処遇グループ単位で AskUserQuestion (multiSelect) を使い、「このグループを承認 / 除外したい項目がある」の粒度で聞く。除外指定があった項目だけ個別に扱う。承認された項目が 1 つもなければ、手順 5〜6 を行わず現状の報告だけして終わる。

### 5. バックアップ

適用前に必ず取る。保存先はプロジェクトの `.claude/` 直下 (cwd の git ルート、リポジトリでなければ cwd)。ユーザがバックアップの存在に自然に気づける場所に置く。

```sh
BK_DIR=<プロジェクトルート>/.claude
mkdir -p "$BK_DIR"
cd "$(dirname "$MEMDIR")" && zip -r "$BK_DIR/$(date +%Y%m%d-%H%M%S)-memory.zip" "$(basename "$MEMDIR")"
# 復元: cd "$(dirname "$MEMDIR")" && rm -rf "$(basename "$MEMDIR")" && unzip <上記 zip>
```

復元コマンドを報告に含める。バックアップが取れなければ適用に進まず中断する。過去の実行のバックアップが残っていたら、古いものの削除を報告時に提案する。

### 6. 適用 — 削除 → 統合・昇格・移管 → 平易化 → レビュー → index 再生成

この順序を守る。消すものを書き直さない、統合で文面が変わるものを先に平易化しない。

1. **削除**: 承認されたものだけ `rm` する
2. **統合・昇格・移管**: merge は統合後ファイルを書いて元ファイルを消す。promote は直書き知見を個別ファイルに書き出す。relocate は移管先に書いてからメモリを消す。新規ファイルの規約:
   - ファイル名は内容を表す短い kebab-case。frontmatter の `name` はファイル名 (拡張子なし) に一致させる
   - `description` は 1 行。`metadata.type` は内容から選ぶ (user / feedback / project / reference)
   - feedback / project は本文に **Why:** と **How to apply:** を持たせる
   - merge では `metadata.mergedFrom` に元の `name` を列挙する。既存メモリに共通するその他のキー (例: `node_type`) は揃えて付け、由来の分からないメタデータ (例: `originSessionId`) は捏造せず省略する
3. **平易化** (サブエージェントにオフロード可): rewrite 対象を書き直す
   - 事実 (パス・コマンド・値・日付・エラーメッセージ) は一字も落とさない。古くなった事実は現実に合わせて更新する
   - 圧縮表記・矢印チェーン・1 文への詰め込みをやめ、完結した文にする
   - 比喩・擬人化・独自のレトリックを、プロジェクトやリポジトリで使われている平易な語彙に置き換える
   - 相対日付は絶対日付にする
   - 本題から逸れた追記は、トリアージで決めたとおり分離または削除する
   - frontmatter は新規ファイルの規約 (上記 2) に合わせて正規化する。既存の他のキーは残す
4. **レビュー**: 新規作成・書き換えした全ファイル (サブエージェントの成果物を含む) をメインセッションで Read し、元の文面と突き合わせて事実の欠落・改変がないか確認する。見つけたらメインセッションで直してから先へ進む
5. **index 再生成**: MEMORY.md を作り直す。個別メモリ 1 件につき 1 行 `- [タイトル](file.md) — 要点`。元の index の節見出し (`## Reference` など) は維持してよい。要点は全角換算 40 文字未満で「何についてのメモリか」だけを書き、コマンド・値・手順は書かない (詳細は本文ファイル側にある)。タイトルと要点の文言も平易化のルール (上記 3) に従い、比喩や擬人化を新しく持ち込まない。全個別メモリが index に載っていること、リンク先が実在すること、本文中の `[[link]]` が残存メモリの `name` と一致することを確認する

### 7. 報告

- before / after: ファイル数・合計バイト数・MEMORY.md のバイト数
- 削除・統合・移管・書き換えの一覧 (それぞれ 1 行で)
- バックアップの場所と復元コマンド
- 次回の目安: MEMORY.md が 5KB またはメモリ 20 件を超えたら再実行を勧める
