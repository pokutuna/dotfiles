# Design Doc

プロジェクトに Design Doc のテンプレートや表記規則がある場合は、それに従う。指定がなければ、本文は日本語で書き、セクション見出しには英語名 (Objective, Background, ...) を使う。必要に応じて日本語を併記する。

## 中心原則: 間違いの代償 (Cost of Being Wrong)

設計判断に使う時間と説明の詳しさは、その判断を間違えたときの影響で決める。後から変更するために必要な費用、作業時間、移行の難しさ、利用者への影響を具体的に考える。この影響を「間違いの代償」と呼ぶ。

- 間違いの代償が大きい判断は、制約、選択肢、トレードオフを詳しく書く。未決定ならユーザーに質問する。例えば、20 万行を実装した後でプログラミング言語を変更するには、大規模な書き直しが必要になる。
- 間違いの代償が小さい判断には、妥当な案を選び、長い議論を書かない。例えば、一覧表示を「もっと読む」方式にするか無限スクロールにするかは、利用者の反応を確認してから比較的短い時間で変更できる。

間違いの代償が小さくても、実装前に確認が必要な判断は Open Issues に残す。

## 進め方

1. 設計する対象を確認する。利用者が操作する機能、内部リファクタリング、障害や情報漏洩のリスクがある機能では、必要な説明が異なる。
2. プロジェクトのテンプレートにある必須セクションを書く。テンプレートがなければ骨格セクションを使い、内容次第セクションは設計対象との関係と間違いの代償を確認して選ぶ。
3. 仕様が決まっていない箇所と、設計を決めた後も懸念が残る箇所を特定する。間違いの代償が大きい判断は `AskUserQuestion` で質問し、各選択肢によって何が変わるかを説明する。代償が小さい判断には、妥当な案を補う。
4. Design Doc を読み直し、品質基準を満たしているか確認する。

ユーザーが明示した要件を黙って変更しない。要件の矛盾や実現が難しい点を見つけた場合は、その影響と代替案を示して確認する。決まっていない部分は、間違いの代償に基づいて補う。

自動処理など、ユーザーから回答を得られない状況では質問しない。未決定の項目には妥当な値を仮定する。間違いの代償が大きい項目は Open Issues に「要確認」として残し、何を仮定したかを書く。

依頼が「漏れの洗い出し」であれば、次のセクション群をチェックリストとして使う。欠けている検討事項と、間違いの代償が大きい未決定事項を指摘する。この場合は、Design Doc 全体を作成しなくてよい。

## セクションの選び方

すべての Design Doc に、すべてのセクションを書く必要はない。プロジェクトのテンプレートがなければ骨格セクションを原則として書き、内容次第セクションは設計対象との関係と間違いの代償を確認して選ぶ。例えば、内部ライブラリには利用者の操作シナリオが不要な場合がある。外部入力を扱わないバッチ処理では、Security セクションが不要な場合がある。該当しないセクションは、空欄や `N/A` で残さずに省く。

省いたセクションを Design Doc 内に列挙しない。ただし、読者が必要だと考えそうな主要セクションを省く場合は、Background または Non-Goals に理由を書く。例えば、Scenarios や Security を意図的に省く場合が該当する。省略理由だけをまとめたセクションは作らない。

## 各セクションの書き方

以下は、プロジェクト固有のテンプレートがない場合に使う標準的なセクションである。テンプレートがある場合は、その構成とセクション名に合わせ、各項目の説明だけを適用する。

### 骨格

#### Title

文書冒頭の H1 には、設計する機能、変更、移行などの対象が分かるタイトルを書く。プロジェクトに命名規則があれば、それに従う。

#### Metadata

ユーザーの要求やプロジェクトのテンプレートに従う。指定がなければ省いてよい。

#### Objective

プロジェクトの目的を一文で書き、文書の冒頭に置く。開発チーム以外の利害関係者にも分かる言葉を使う。

> 例: Trogdor Web サーバと Postgres データベースの間にキャッシュ層を追加し、アプリケーションのパフォーマンスを改善する。

#### Background

このプロジェクトが必要な理由と、解決する問題を書く。過去に同じ問題を解決しようとした取り組みがあれば、その結果も書く。後の設計判断で前提となる情報をここにまとめる。

同僚が文書を読む前に、口頭で何を説明する必要があるかを考える。その内容を文書の冒頭に書く。

問題の大きさを確認できる測定値や観測結果があれば記載する。「遅い」とだけ書かず、「レスポンス時間が 100 ms から 600 ms に増えた」のように書く。ページロード時間の 80% をデータベース参照が占めるなど、原因を判断できる測定結果も示す。

#### Goals

採用する技術ではなく、プロジェクトによって得たい結果を書く。利用者、開発チーム、会社に何がもたらされるかを説明する。各項目は「最小化する」「共有できるようにする」「維持する」などの動詞で始める。

- ✕ Kubernetes をインフラに導入する (実装)
- ◯ 新バージョンのデプロイに起因する障害を最小化する (インパクト)

> 例:
> - 家族の写真や動画を親族や親しい友人と共有できるようにする。
> - 複雑さを最小化し、PC に不慣れな親族でも安心して使えるようにする。
> - 全データを非公開に保ち、許可されたユーザーだけがアクセスできるようにする。

#### Non-Goals

このプロジェクトで扱わないことを書く。読者が対象に含まれると誤解しそうな項目を選び、否定形で明示する。必要であれば、対象外にする理由も書く。

> 例:
> - 商用の写真共有アプリは作らない。
> - 過去アップロードの URL リンクは保持しない。
> - 複数の家族が同一サーバを共有することは許可しない。

### 内容次第 (該当時のみ・設計の表現)

#### Scenarios

完成後に、利用者や外部システムがどのように操作するかを具体的な順序で書く。利用者の操作や外部システムとのやり取りがある場合に、このセクションを設ける。順序が重要な場合は番号付きリストを使う。

> 例:
> 1. 親が Web アプリを開く。
> 2. 親がメインページの「アップロード」ボタンをクリックする。
> 3. Web アプリが、アップロードするファイルの選択画面を表示する。

#### Diagrams

データの流れやコンポーネント間の関係を図で示す。Excalidraw、draw.io、Google Drawings、Mermaid、D2、Graphviz など、後から編集できる形式を使う。ホワイトボードの写真は、内容を修正できないため使用しない。図には、描画ファイルまたは生成に使ったコードへのリンクを付ける。チームのメンバーが同じ図を再生成し、修正できる状態にする。

#### Interfaces

利用者や他のシステムが使う接点を書く。対象には、UI、API や CLI の動作、ファイル形式が含まれる。内部実装をすべて説明する必要はない。呼び出し側が依存する入力、出力、エラー、互換性を明確にする。UI は精密なモックを作らず、簡単なスケッチや操作時の振る舞いを示してもよい。

#### Related Documents

テスト計画や機能仕様など、設計に関連する文書へのリンクを記載する。

#### Glossary

新メンバーや外部読者向けに、馴染みのない用語を定義する。

### 内容次第 (該当時のみ・技術仕様)

実装後に変更することが難しい技術判断は、理由と影響を詳しく書く。

#### Constraints

予算、既存のインフラ、他のシステムへの依存など、設計で変更できない条件を書く。それぞれの条件が、選べる設計をどのように制限するかも説明する。

将来の規模が設計判断に影響する場合は、この設計を維持したい期間を書く。その時点で想定する利用者数、データ量、リクエスト量も示す。

#### Dependencies / Infrastructure

プログラミング言語、ハードウェア、永続ストレージ、外部サービスなど、設計が依存するものを書く。実装後の変更に大規模な書き直しやデータ移行が必要になる依存関係は、選定理由とともに詳しく説明する。容易に差し替えられる依存関係には、長い説明を加えない。

#### Service Level Objectives (SLOs)

「速い」「高性能」「モバイルで快適」など、達成したか判断できない目標を使わない。可用性、レイテンシ、処理件数などについて、測定方法と目標値を書く。測定する環境や対象の操作も明記する。

> 例:
> - 目標: 99% の可用性。
> - ビューポート内のサムネイルは、1 Gbps 接続のデスクトップで 400 ms 以内に表示する。

#### Timeline

作業をマイルストーンに分け、各段階で確認できる成果を示す。設計上の誤解を早く発見できる順序にする。例えば、ダミーデータを使った UI を先に作ると、バックエンドを実装する前に操作方法の認識を確認できる。必要であれば、各マイルストーンで実装するものと、後の段階まで実装しないものを書く。

### 内容次第 (該当時のみ・リスクとコンプライアンス)

セキュリティ、プライバシー、法令順守に関するリスクがない場合は、この分類のセクションを省く。

#### Security

想定する攻撃者と、攻撃によって起きる影響を書く。外部から受け取ったデータを処理する箇所と、異なる権限の間でデータが移動する箇所も示す。ある脅威への対策が不要だと判断した場合も、その理由を書く。プロジェクトに脅威を記述する形式がなければ、脅威ごとにタイトルを付け、`Scenario:` に攻撃が成立する条件と影響を、`Mitigations:` に対策を整理してもよい。

> 例:
> #### 未認証の攻撃者が S3 バケット内の写真を発見する
> Scenario: バケットが公開設定だと、URL を推測した第三者が写真を閲覧できる。
> Mitigations:
> - バケットを非公開にし、署名付き URL でのみアクセスさせる。

#### Privacy

システムが扱う機微データを特定する。誰がアクセスできるか、どのくらいの期間保持するか、保存時と通信時にどのように保護するかを書く。対策を書く前に、漏洩や目的外利用によって誰にどのような影響があるかを説明する。

#### Legal

金融や医療などの規制が適用されるかを確認し、設計で満たす必要がある条件を書く。使用する OSS のライセンスが、配布方法やソースコード公開の要否に与える影響も確認する。

### 内容次第 (該当時のみ・運用と監視)

本番環境で継続的に運用するシステムなど、異常の検知や障害調査が必要な対象で書く。

#### Monitoring / Alerting

システムの状態を判断するために監視する指標と、異常を検知する条件を書く。SLO がある場合は、その達成状況を測定する方法を示す。アラートには、発生条件、重要度、通知先を記載する。対応が不要な状態でアラートが繰り返し発生しないように、評価期間や抑制条件も検討する。

> 例: 95 パーセンタイルのレイテンシが 5 分間継続して 3 秒を超えた場合に、アラートを発生させる。

#### Logging

障害調査や監査に必要なイベントを特定し、記録する内容とログレベルを書く。ログを保持する期間と、閲覧できる人も決める。パスワードや個人情報など、ログに記録してはならないデータを明記する。

### 内容次第 (該当時のみ・課題管理)

採用する設計を決めた後も懸念が残る場合は、関連するセクションに記載する。問題が起きる条件、起きた場合の影響、検知する方法、対応する方法を書く。複数のセクションに関係する懸念がある場合だけ、Concerns セクションを設ける。

#### Open Issues

未解決の設計上の問題を書く。各項目で、決める必要があること、検討中の選択肢、次に確認することを説明する。必要な情報が不足している場合は、誰から何の回答を得る必要があるかを書く。

判断を意図的に後回しにする場合は、今決めない理由を書く。誰が判断するかと、判断する時期または条件も明記する。

レビューで設計の説明が誤解された場合は、コメントへの返信だけで済ませず、Design Doc の本文を修正する。判断が決まっていない場合は、会話の内容をそのまま転記せず、未解決の問題と選択肢を Open Issues に整理する。

#### Resolved Issues

Open Issue が決着したら、決定内容を関連する設計のセクションに反映する。プロジェクトの運用で求められる場合や、判断の履歴自体が読者に必要な場合は、決定、判断基準、検討した有力な選択肢をこのセクションに要約する。制作中の会話や、提案が変わった順序は残さない。

> 例:
> Decision: Sendamatic を採用する。配信成功率が要件を下回る場合は Amazon SES に移行する。
> Criteria: 配信成功率、運用コスト、障害発生時の調査方法。
> Candidates: Sendamatic、Amazon SES。

#### Alternatives Considered

採用しなかった有力な案と、採用しなかった理由を書く。各案について、判断に影響した利点と欠点を簡潔に説明する。会話に登場したすべての案を網羅する必要はない。文章、表、利点と欠点の対比など、設計に合う形式を選ぶ。

> 例:
> #### Google Photos
> - 利点: 写真が収まれば無料で利用できる。
> - 欠点: Google への依存が生じる。

## 品質基準

書き上げたら、次の基準で確認する。

- Design Doc だけで設計の目的と前提を理解できること。文書の冒頭に、目的、解決する問題、設計を理解するために重要な情報を書く。他のチームや新しいメンバーにも分かる言葉を使う。専門用語が必要なら、その意味を説明する。
- 設計判断に必要な詳細を書くこと。ただし、関数単位の処理や、実装時に安全に決められる詳細までは書かない。Design Doc は、実装を始める前に重要な判断を確認するための文書である。
- 文章だけでは関係を追いにくい場合に図を使うこと。コンポーネント間の関係、データの流れ、複数の段階がある処理を図で示す。
- 条件、動作、理由、結果を一文や名詞の列挙に詰め込まないこと。誰が何をし、なぜその結果になるのかが分かるように文を分ける。
- 制作時の会話を残さないこと。対話中に得た知見が読者にも必要なら、対象の制約、判断理由、トレードオフとして書き直す。
